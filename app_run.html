☁️ Cloud ingestion, Secrets & CI/CD

The pipeline is now fully cloud-native: the daily trigger runs in Cloud Scheduler, the fetch runs in a news-fetcher Cloud Run service, the Tavily key lives in Secret Manager, and every deploy goes through GitHub Actions with keyless auth (Workload Identity Federation). No local cron, no stored keys.

New architecture

Cloud Scheduler (daily-news-fetch, 07:00)
   └─ OIDC POST ─▶ news-fetcher (Cloud Run)   ← reads tavily-api-key from Secret Manager
                      └─ uploads ai_news_{date}.json ─▶ source_raw_123456/incoming/
                             └─ Pub/Sub ─▶ raw-file-processor ─▶ destination/processed/ai_news_{date}.html

GitHub Actions (one gated pipeline, ci-cd.yml):
   push / PR ──▶ lint (ruff+shellcheck) + test (pytest)
                        └─ if both pass AND ref is main / v* tag ──▶ deploy (both services, WIF)
Already done for you: the required APIs are enabled and your Tavily key is stored in Secret Manager as tavily-api-key. The steps below are idempotent.

Bootstrap (local, once) vs. deploy (CI, every push)

Two kinds of work are deliberately kept separate — this is why some steps run locally and are not in the ci-cd.yml pipeline:

One-time bootstrap — infrastructureEvery-push deploy — app code
Create service accounts & IAM, the secret, buckets, Pub/Sub, the scheduler, and the WIF trust. Build the container and roll out the Cloud Run service.
Needs admin rights · rarely changes · you run it once. Needs only deploy rights · changes constantly · GitHub Actions runs it.
make setup · make setup-ingestion · make wif ci-cd.yml deploy job — push to main or tag v*

Why not do everything in the deploy pipeline?

  • Least privilege. Creating service accounts and granting project IAM needs admin roles. Giving those to the CI identity would let any push mint accounts and grant itself permissions — far too much blast radius. CI is kept to deploy-only powers on purpose.
  • WIF is a chicken-and-egg. Workload Identity Federation is the very thing that lets GitHub authenticate to GCP, so it can't be created by GitHub. make wif must run once with your own admin credentials — there is no way around this.
  • One-time vs. every-time. Infrastructure is created once and left alone; baking it into every deploy would re-run setup on every code push for no benefit.
Bottom line: the local steps are a one-time bootstrap, not an ongoing chore. After make setup-ingestion runs once, every future code change deploys purely through GitHub Actions. You can even run the bootstrap in GCP Cloud Shell instead of your Mac — it only needs your admin login.

A) One-time bootstrap — run in this order

# 1. base pipeline (buckets, topic, processor, subscription, notification) — if not already done

C) Deploy — two ways (gated by lint + tests)

Everything is one workflow, .github/workflows/ci-cd.yml, with three jobs. The deploy job declares needs: [lint, test], so it runs only if lint and tests both pass — and only on main or a v* tag.

TriggerHowResult
Any push / PR (any branch)—lint + test run (no deploy)
Merge / push to mainnormal PR merge or pushlint + test → deploy both services
Tag v* from any branchsee belowlint + test → deploy that tagged commit
# release from any branch by tagging:
git tag v1.0.0
git push origin v1.0.0

D) Lint + tests on every push (the gate)

ci-cd.yml runs ruff + shellcheck (lint) and pytest (unit tests) on every push/PR. A failing check blocks the deploy. Run the same checks locally first:

make lint       # ruff check .
make test       # pytest -q
Secrets stay out of git. The Tavily key lives only in Secret Manager and is injected into news-fetcher at deploy time (--set-secrets). Your local .env is gitignored and never pushed.

5 Run the pipeline manually ⭐

This is all you need — no cron required. The moment a file lands in the source bucket, Pub/Sub triggers Cloud Run and the result appears in the destination bucket (verified: it processes in ~5 seconds).

The whole loop: push a file → incoming/ → Pub/Sub → Cloud Run → processed/. You control when by choosing when to push.

Option A — fetch fresh AI news and push (one command)

make news

This fetches AI news (Tavily → Google News RSS fallback), writes data/ai_news_YYYY-MM-DD.json, uploads it to gs://source_raw_123456/incoming/ (that upload is the trigger), and logs to ingestion/logs/.

Option B — push your own records (any file)

Drop any file into the source bucket's incoming/ folder and it processes immediately:

gcloud storage cp /path/to/yourfile.json gs://source_raw_123456/incoming/

Then watch it process

# the processed result appears here within seconds:
gcloud storage ls gs://destination_raw_123456/processed/

# and the Cloud Run logs show it working:
make logs
Only files under incoming/ trigger the pipeline. The Cloud Run outputs go to processed/ in the other bucket, so there is no loop.
Just want to preview the fetched news locally without pushing? make fetch-local → writes data/ai_news_preview.json (no upload, no trigger).

6 Legacy: local cron (superseded by Cloud Scheduler)

You no longer need this. The daily trigger now runs in GCP via Cloud Scheduler — see the Cloud ingestion & CI/CD section. Kept here only for a fully-local setup.

Recommended instead: make setup-ingestion creates a Cloud Scheduler job that runs the fetch daily in the cloud — no Mac, no cron, no Full Disk Access.
macOS caveat (local cron only): if the project lives under ~/Documents, cron is blocked by macOS privacy ("Operation not permitted") unless you grant Full Disk Access to /usr/sbin/cron, or move the project out of ~/Documents. Manual runs (Step 5) have no such restriction.

a) Confirm the paths inside ingestion/fetch_and_push_news.sh

which gcloud                       # must match GCLOUD in the script
ls /opt/anaconda3/envs/mcp/bin/python   # must match MCP_PYTHON in the script

b) Install the cron line

make install-cron        # prints the exact line, then:
crontab -e               # paste it, save, quit

The line it installs:

0 7 * * * /path/to/your-repo/ingestion/fetch_and_push_news.sh
macOS required step: give cron disk access, or it can't read your project folder.
System Settings → Privacy & Security → Full Disk Access → add /usr/sbin/cron (press ⌘+Shift+G in the file picker and type the path).

Confirm it's scheduled:

crontab -l

9 Update / redeploy the processor

When you change the processing logic, redeploy just the Cloud Run service.

The service is a FastAPI app (served by uvicorn) in services/raw-file-processor/main.py. The process_data() function is where your real transformation goes. Then:

make deploy
Stack: FastAPI + uvicorn + google-cloud-storage (see services/raw-file-processor/requirements.txt).
